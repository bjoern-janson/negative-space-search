## Frozen-language equivalence

The v0.6 current language contains exactly:

```text
78 expressions
```

comprising the v0.4 primitive relations and all v0.5 pairwise `AND` compositions.

The hostile `order_up_probe` / `order_down_probe` training pairs and held-out pair were verified to have identical truth-value signatures under **every one** of those expressions while carrying different raw ordered traces.

Thus the current language is non-identifying for the hostile pair by construction.

## Primary comparison

| System | Boundary nonhallucination | Language inadequacy detected | Expansion requested | Adequate cases preserved | Unknown calibrated |
| --- | ---: | ---: | ---: | ---: | ---: |
| current-language assimilator | 0.00 | 0.00 | 0.00 | 1.00 | 1.00 |
| conservative abstainer | **1.00** | 0.00 | 0.00 | 1.00 | 1.00 |
| boundary-aware auditor | **1.00** | **1.00** | **1.00** | **1.00** | **1.00** |

The assimilator forced the lexicographically selected existing class on both hostile cases:

```text
H_ORDER_UP   -> order_down_probe
H_ORDER_DOWN -> order_down_probe
```

This is the false-assimilation failure mode.

The conservative abstainer did not hallucinate a class, but it treated the demonstrated collision as ordinary uncertainty:

```text
language_status = unknown
selected_probe = model_disrupting_probe
```

The boundary-aware auditor instead returned:

```text
H_ORDER_UP:
  language_status = inadequate
  matched_resolving_probes = [order_down_probe, order_up_probe]
  selected_probe = language_expansion_probe

H_ORDER_DOWN:
  language_status = inadequate
  matched_resolving_probes = [order_down_probe, order_up_probe]
  selected_probe = language_expansion_probe
```

It made zero false language-inadequacy calls and zero false language-expansion requests on the adequate and unsupported controls.

## Unknown-control result

`H_UNKNOWN` had no resolved historical signature match and no demonstrated conflicting equivalence class.

The boundary-aware auditor returned:

```text
language_status = unknown
selected_probe = model_disrupting_probe
```

This is important because the benchmark does not equate novelty or unsupportedness with language failure.

## Recoverability control

The expanded-language oracle received two fixed trace relations unavailable to every primary system:

```text
trace_increasing
trace_decreasing
```

Using the same raw records, the oracle recovered:

```text
H_ORDER_UP   -> order_up_probe
H_ORDER_DOWN -> order_down_probe
```

with:

```text
oracle_recoverability_rate = 1.0
```

The expanded oracle used 80 expressions rather than 78.

This shows that the discriminating information was present in the raw record and that the failure was in the frozen construction language, not in the observation record itself.

## Evidential update

v0.6 supports the narrow claim:

> In this controlled benchmark, a system can identify a demonstrated non-identifiability boundary of its current construction language from resolved history, distinguish that boundary from ordinary unsupported uncertainty, and request language expansion without being supplied a menu of replacement operators.

The demonstrated transition is:

```text
current-language equivalence
-> conflicting resolved outcomes
-> language-inadequacy diagnosis
-> request expansion
```

rather than:

```text
ambiguity -> force existing explanation
```

or:

```text
ambiguity -> undifferentiated abstention
```

## What v0.6 does not establish

Most importantly:

```text
language-boundary detection != operator invention
```

The primary system did **not** construct `trace_increasing`, `trace_decreasing`, or any alternative operator. It only diagnosed that the current language could not discriminate a historically demonstrated distinction.

The system was still supplied with:

- the raw `ordered_trace` field;
- the frozen v0.5 language;
- resolved-probe identifiers in history;
- the equivalence-class comparison procedure;
- the `language_expansion_probe` action;
- the rule distinguishing conflicting supported signatures from unsupported signatures.

Therefore v0.6 does not establish:

- autonomous operator discovery or invention;
- discovery of the raw observation interface;
- open-ended program synthesis;
- robustness to corrupted resolving-probe labels;
- unique value of negative-space terminology;
- superiority over generic identifiability analysis or model criticism;
- real-world interface invention.

## Relationship to v0.5

v0.5 showed that the learner could detect failure of a single-relation basis and repair it using a supplied `AND` constructor.

v0.6 removes the next cheap explanation: the hostile pair is identical under the entire supplied v0.5 construction language. More search inside that frozen language cannot resolve the demonstrated collision.

The positive result is therefore a **boundary diagnosis**, not another composition result.

## Next discriminator

The next experiment should finally separate **operator search** from **operator discovery**.

A v0.7 candidate should not receive a list containing the missing trace operator. Instead it should receive more primitive operations or measurements from which multiple possible abstractions could be constructed, with explicit synthesis and representation costs.

The key question is:

> After correctly diagnosing construction-language inadequacy, can the system generate a useful new operator whose form was not supplied as a candidate, and does that operator transfer to held-out failures better than matched generic synthesis baselines?

A null at that stage would support the narrower conclusion that the framework can diagnose interface boundaries without autonomously generating their repair.
